# Warehouse journey snapshot

This snapshot combines the existing `parcel-warehouse` Table/View pair with
validations of those same names. It is needed to check the newly continuous
reader route; it is not a replacement for the existing incremental fixture.

Reader path:

- [First Table and View](../../docs/warehouse/first-project.md): initialise the
  disposable Fabric items once, then use `Parcel.StatusEvent.sql` and
  `Parcel.CurrentStatus.sql`. The Table has three deterministic event rows; the
  View yields `P-1001 / In transit / Central` and `P-1002 / Delivered / South`.
- [Tests](../../docs/warehouse/tests.md): add the supplied `tests/` and
  `assumptions/` directories to that project. The expected fixture state is a
  passing comparison and no unknown statuses.
- Deliberate finding: replace the installed Test's source file with
  `failure/Parcel.CurrentStatusMatches.sql`, then Check, Build and Test as shown
  in the page. The expected discrepancy is one missing and one unexpected row
  for `P-1002`. Restore the passing Test to return to the prior checkpoint.
- [Loading changes](../../docs/warehouse/incremental.md): switch explicitly to
  `../parcel-incremental-warehouse`, its separate external `ParcelSource` and
  disposable `ParcelOperations`/`ParcelCatalogue` targets. `CurrentStatus` is a
  keyed Table there, not this snapshot's View. Do not overlay the snapshots.

`workspace-config.yml` matches the bindings generated by the first page's
initialisation command. Adjust the workspace for your disposable environment.
The snapshot neither provisions those items nor publishes an Environment.

## Local acceptance

Run with the Python environment supplying the pinned Weaver dependencies:

```bash
PYTHONPATH="$WEAVER_CHECKOUT/src" python examples/parcel-warehouse-journey/check.py \
  --weaver-checkout "$WEAVER_CHECKOUT"
```

Run that command from the documentation repository root. The checker compares
published blocks with fixture files, parses every published SQL program and
Weaver declaration, generates the two Table load installers, parses CLI/config
examples, and assembles first/passing/finding/restored snapshots. It calls real
Weaver Check and verifies inferred dependencies with sockets blocked. It also
checks the unchanged incremental snapshot and confirms fixture hashes stay
unchanged. The deliberately wrong expected rows still pass Check: finding the
discrepancy requires Test against deployed data.

No Build, Load, Test, Health, SQL endpoint or bookmark readback is executed
against Fabric by this checker. Row/status results above are reader expectations,
not local service observations. Weaver's T-SQL parser classifies statements and
result queries; it does not validate native Warehouse SQL grammar.
